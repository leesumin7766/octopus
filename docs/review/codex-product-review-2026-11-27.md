# Octopus 사용자 관점 독립 검토 및 제안서 비교

작성: 2026-11-27 / Codex / dev `126b3c7`.
제품 코드를 변경하지 않은 검토다. 첨부 제안서를 읽기 전에 현재 코드와 화면 문구를 먼저 살펴보고, 그 후 Claude Code의 ‘기능·이름 기준 검토’와 대조했다.
실제 창을 클릭한 인수시험 결과가 아니라 코드 경로에 근거한 평가다. 이전 보고서의 UI 미검증 항목을 이번 검토로 통과시키지 않는다.

## 1. 판단 기준과 결론

기능 개수보다 사용자가 결과를 이해하고, 실수를 복구하고, 자신의 공간을 구성하며, 실패 후에도 작업을 이어갈 수 있어야 한다.
현재 핵심 문제는 기능 부족보다 **추가→확인→편집→완료→복구 흐름의 단절과 화면별 동작 차이**다.
용어·색상 정리는 필요하지만 데이터 보호와 작업 흐름 복구보다 먼저 전면 리팩터링할 이유는 없다.

## 3. 첨부 제안서의 적절성

### 동의하는 부분

- 달력/캘린더 통일, 할 일의 notes를 '설명'으로 바꾸기, 뜻이 겹치는 '취소' 구분.
- 홈 완료 복구와 추가 결과 안내, 취소 상태의 영구 조회 경로 마련.
- 내부 bucket을 오류 없이 날짜·사용자 의도로 맞춰 주기. 사용자가 내부 저장 규칙을 맞출 필요 없음.
- 메모·루틴 화면의 색상·간격·포커스·오류 표현을 현재 디자인에 맞추기.
- 용어와 동작 기준 문서화. 단, 모든 새 문구를 사용자 승인 대상으로 삼는 규칙은 불필요한 작업 중단을 만든다. 의미·정책 변경만 확인하면 된다.

### 그대로 채택하면 안 되는 부분

| 제안 | 판단과 대안 |
|---|---|
| 모든 Enter는 저장/보내기 | 여러 줄 메모에서는 Enter 줄바꿈이 자연스럽고 실수 저장을 막는다. 한 줄 추가는 Enter, 여러 줄 문서는 Enter 줄바꿈·Ctrl/Cmd+Enter 저장처럼 목적별 기준을 둔다. 키 설명과 명시적 저장 버튼 제공 |
| 모든 추가를 동일 QuickInput으로, 시각 칸 제거 | 날짜를 눈으로 골라 넣는 사용자를 위해 시각 선택은 유용하다. 자연어와 명시적 날짜·시각 입력을 함께 제공할 수 있다. 선택 날짜가 기본일 때 '내일'의 해석과 우선순위를 저장 전 표시해야 함 |
| 설명문 전면 금지 | 필수 안내까지 없애면 초보자와 키보드 사용자가 기능을 발견하기 어렵다. 연결 권한·덮어쓰기·업데이트 재시작·반복 동작은 짧은 설명을 유지. placeholder는 입력 후 사라져 라벨 대체 불가 |
| 모두 동일 TaskRow, 동일 완료 이동 | 공통 로직과 시각 원칙은 공유하되 달력과 루틴 기록·오늘 집중 화면은 목적이 다르다. 체크 직후 이동하는 정책은 포커스/실수 복구를 먼저 검증. 공통 컴포넌트화 자체를 제품 목표로 삼지 않음 |
| 취소 항목을 완료 보기에 섞기 | 되찾기는 필요하지만 완료 수치와 의미를 왜곡하면 안 된다. '종료됨' 아래 완료/안 하기로 함 필터 또는 별도 보관 목록이 더 명확. 취소를 완료 통계에 포함하지 않음 |
| 수신함과 나중에 즉시 합치기(D1) | 둘은 날짜 유무가 같아도 정리 전과 의도적으로 미룬 상태라는 차이가 있다. 이름·설명·기본 이동을 먼저 개선하고 실제 혼동을 확인한 뒤 축소 |
| 루틴과 반복 모델 합치기(D2) | 미완료 이월만의 차이가 아니다. 회차 생성, 날짜별 기록, 완료 취소, 중단·수정 영향도 다르다. 통합 설정 경험부터 검토하고 DB 모델 통합은 후속으로 분리 |
| 루틴 14일 표를 기호로 대체·범례 삭제 | 날짜별 기록을 읽는 정보량이 줄 수 있다. ○가 미완료/미실행/미해당 중 무엇인지 더 모호해진다. 숫자·텍스트·접근성 이름과 필요 시 범례 유지 |
| hover일 때만 행 동작 표시 | focus에서도 제공하되 터치에서 접근 가능해야 한다. 더보기 버튼 등 지속적인 진입 경로 마련 |
| 모든 동사를 '추가/삭제'로 통일 | 메모→할 일은 '할 일로 만들기', 연결 해제와 데이터 삭제는 다른 의미다. 같은 행동은 통일하되 다른 결과의 행동을 같은 이름으로 덮지 않음 |
| 격주 등 자연어 확장을 소규모로 평가 | 파서 구현량과 인수 범위는 다르다. 기준일·요일 조합·미리보기·완료 후 다음 회차까지 회귀 검증 필요 |
| 기록 탭을 바로 추가(D4) | 먼저 가져오기/내보내기/AI 실행의 결과·오류와 대상 열기를 기존 화면에 제공. 별도 기록 탭은 실제 필요와 보관 정책을 정한 후 추가 |

### 사실관계 보충

- 할 일 탭의 '취소'에는 짧은 undo가 이미 있다. 제안서의 핵심 문제는 '전혀 되돌릴 수 없음'이 아니라 시간이 지난 뒤의 지속 복구 경로 부재다.
- 메모 검색·검색 강조, 반복 규칙 편집, 로컬 달력·타일 바로가기·수동 업데이트는 현재 구현돼 있다. 예전 검토의 미구현 목록을 그대로 재사용하면 안 된다.
- 여러 화면에서 같은 Task를 보는 것 자체는 기능 중복 결함이 아니다. 같은 ID·상태·변경 결과와 예측 가능한 상호작용을 제공하는지가 기준이다.

## 4. 권장 개발 순서와 완료 기준

1. **데이터·실수 보호:** 초안 유실, 중복 저장, 설정 실패, 취소 조회/복구, 업데이트 실패 안내. 지연·실패·재시작 테스트를 먼저 작성.
2. **핵심 작업 끝맺기:** 홈 추가 결과 및 대상 열기, 제목→상세, 메모→할 일 이동, 화면별 완료 복구. 최소 클릭으로 원래 작업으로 돌아오는지 확인.
3. **용어·디자인 정돈:** 달력/설명/안 하기로 함, 메모·루틴 디자인 토큰, 입력 목적별 단축키. 기존 데이터 모델을 유지하며 적용.
4. **찾기와 달력 일치:** 로컬 검색, Google 오류·갱신 일치, 날짜 이동 취소 원자성, 미래 반복 표시 정책.
5. **후속 사용자 구성·운영:** 홈 카드 숨김/교체, 백업·복원. 보기/반복 모델 통합·기록 탭은 별도 설계.

각 항목은 정상 동작뿐 아니라 취소·실패·재시도·지연 응답·재시작을 포함해 검증한다. 자동 테스트와 실제 Electron 조작·작은 창/배율·키보드 검증은 별도 기록한다.
